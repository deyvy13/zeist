## La verdad incómoda: programar te va a cambiar la carrera

Un ingeniero civil que sabe programar (aunque sea básico) hace las mismas tareas **en la mitad del tiempo**. Y lo más importante: puede automatizar lo que a sus compañeros les toma horas. Esa asimetría es enorme.

- Si eres empleado: **subes tu valor por hora**. Los ingenieros que automatizan cobran más.
- Si tienes tu oficina: **aumentas capacidad sin contratar**.
- Si eres freelance: **entregas más rápido** y compites mejor en precio o en margen.

Y la parte buena: **con IA nunca fue más fácil aprender**. No hace falta hacer un máster.

<TopicCard step="1" title="1. Por qué programar cambia tu carrera de ingeniero" time="~4 min">

Los datos duros:

- Tareas repetitivas en oficina de ingeniería típica: **40-60% del tiempo del equipo**.
- Salario premium de ingenieros con habilidades de programación: **+30-70%** según región.
- Reducción de errores humanos automatizando: **60-90%** para tareas típicas.

Y sobre todo: **te cambia el chip**. Empiezas a ver problemas como sistemas — con inputs, procesos y outputs. Esa mentalidad, más allá del código, te vuelve mejor ingeniero.

**Lo que NO significa programar como ingeniero civil:**
- No significa ser desarrollador de software.
- No significa dejar la ingeniería.
- No significa aprender 20 lenguajes.
- Significa **usar programación como una herramienta más**, como el AutoCAD o el Excel — igual de natural.

<TopicCard step="2" title="2. Diez ideas de automatización que valen la pena (con % de tiempo ahorrado)" time="~7 min">

Ordenadas de más fácil a más avanzada. Todas viables con Python o Dynamo + IA.

1. **Renombrado masivo de familias / capas / vistas** (Revit / AutoCAD). Antes: 2-4 h. Después: 30 s. **Ahorro: ~99%.**
2. **Exportar tablas de cantidades a Excel con formato corporativo.** Antes: 1-2 h. Después: 10 s. **Ahorro: ~99%.**
3. **Colocar cotas o etiquetas automáticas siguiendo reglas.** Antes: 3-5 h/plano. Después: 5 min. **Ahorro: ~95%.**
4. **Generar perfiles longitudinales cada X metros en Civil 3D.** Antes: 3 h. Después: 15 min. **Ahorro: ~92%.**
5. **Cubicación automática de movimiento de tierras.** Antes: 2 h. Después: 30 s. **Ahorro: ~99%.**
6. **Chequeo de estándares BIM** (naming, categorías, parámetros). Antes: 2 h. Después: 30 s + reporte. **Ahorro: ~99%.**
7. **Generación masiva de láminas con vistas + tablas + membrete.** Antes: 4-8 h. Después: 2 min. **Ahorro: ~98%.**
8. **Detección de interferencias entre disciplinas + reporte.** Antes: 3 h. Después: 15 min. **Ahorro: ~92%.**
9. **Modelado paramétrico de taludes desde polilínea + reglas.** Antes: 4 h. Después: 30 min. **Ahorro: ~87%.**
10. **Exportar puntos topográficos a CSV con clasificación.** Antes: 1 h. Después: 10 s. **Ahorro: ~99%.**

<TopicCard step="3" title="3. Arquitectura simple (sin susto)" time="~7 min">

"Arquitectura de software" suena a algo enorme. Para ti, ingeniero que automatiza, es MUCHÍSIMO más simple. Se resume en:

**Regla única:** organiza tu código en **capas** que hacen una sola cosa cada una.

<AnimatedFlow
  title="Las 3 capas mínimas"
  nodes="Entrada (UI)|Lógica del negocio|Interacción con el software (Revit/Civil 3D)"
  subs="Formularios, botones|Reglas propias|API de Autodesk"
/>

**Traducción a carpetas de tu proyecto:**

```
MiPlugin/
  UI/              (formularios, ventanas, botones)
  Logic/           (tus reglas: "las vigas <3m no cuentan")
  Revit/           (todo lo que toca la API — SetParameter, GetElement)
  Program.cs       (punto de entrada, arma las 3 capas)
```

**¿Por qué esto importa?** Porque el día que Autodesk cambie la API (y siempre cambian), solo tocas la carpeta `Revit/`. Tu lógica y UI quedan intactas. Y si mañana quieres cambiar de C# a otro lenguaje, tu lógica es reutilizable.

**Analogía civil:** es como diseñar un edificio con estructura, arquitectura e instalaciones **separadas**. Si toca cambiar las instalaciones, no rediseñas la estructura. Con código igual.

</TopicCard>

<TopicCard step="4" title="4. Código limpio — explicado con ejemplos, no teoría" time="~8 min">

"Código limpio" son 4 hábitos concretos:

**a) Nombres que dicen la verdad.**

Mal:

```python
def calc(x, y):
    return x * y * 0.18
```

Bien:

```python
def calcular_iva(precio, cantidad):
    return precio * cantidad * TASA_IVA
```

El segundo se lee. El primero te obliga a adivinar qué hace.

**b) Funciones cortas que hacen UNA cosa.**

Mal — una función que hace 5 cosas: leer archivo, filtrar datos, calcular, generar reporte, enviar email.

Bien — 5 funciones:

```python
def leer_datos(archivo): ...
def filtrar_por_categoria(datos, cat): ...
def calcular_totales(datos): ...
def generar_reporte(totales): ...
def enviar_email(reporte, destinatario): ...
```

**c) Constantes con nombre, no números mágicos.**

Mal: `if edad > 18:` (¿por qué 18? ¿qué significa?).

Bien:

```python
EDAD_MAYORIA = 18
if edad > EDAD_MAYORIA:
    ...
```

**d) Comentarios donde importan, no en lo obvio.**

Mal:

```python
# Sumar 1
x = x + 1
```

Bien:

```python
# Las vigas <3m no cuentan por norma interna DGA-2023
if longitud_viga >= LONGITUD_MINIMA_VIGA:
    contador += 1
```

</TopicCard>

<TopicCard step="5" title="5. Componentes reutilizables — escribe una vez, usa cinco veces" time="~6 min">

**El problema:** cada script empieza de cero. Copias y pegas las mismas 30 líneas de siempre para conectar con Excel, para leer un archivo, para armar un reporte.

**La solución:** cuando escribas la misma cosa **dos veces**, es una función. La tercera vez, es un componente.

**Ejemplo real:** todos tus scripts terminan exportando a Excel con el mismo membrete corporativo. Extrae ese código a una función que puedas importar:

```python
# archivo: helpers/excel_corporativo.py
def exportar_con_membrete(datos, ruta):
    """Exporta una lista de datos a un Excel con el
    membrete y estilos corporativos de la empresa."""
    ...
```

Ahora en cualquier script: `from helpers.excel_corporativo import exportar_con_membrete`. Una línea, no 30.

**Efecto compuesto:** con 6-8 componentes bien hechos, cada nuevo script tarda **1/3 del tiempo**. Y todos comparten el mismo estándar corporativo automáticamente.

**Regla de oro:** cada vez que copies y pegues código, párate y pregúntate: "¿esto merece ser una función?". La mayoría de veces, sí.

</TopicCard>

<TopicCard step="6" title="6. Control de versión sin drama (Git en 20 minutos)" time="~4 min">

Si sólo aprendes una herramienta de esta guía, que sea Git. Es el **backup infinito** de tu código.

**Setup fácil (sin terminal):**

1. Instala **GitHub Desktop** (interfaz visual, gratis).
2. Crea una cuenta en GitHub.com (gratis).
3. Crea un repositorio privado para cada proyecto de automatización.
4. Cada vez que algo funciona: **botón "Commit" → botón "Push"**. Listo. Está guardado en la nube.

**Lo que ganas:**

- Si mañana rompes algo, vuelves a la versión de ayer con un botón.
- Trabajas desde otra máquina y todo está sincronizado.
- Si vas a compartir con un colega, es una URL.
- **Nunca más "perdí el archivo"**.

Costo total de aprenderlo bien: 20 minutos + un video de YouTube. Valor: infinito.

</TopicCard>

<TopicCard step="7" title="7. Testing manual mínimo (no te vuelvas QA)" time="~5 min">

No necesitas escribir tests automatizados como un dev senior. Necesitas **un mínimo de disciplina** para no romper cosas.

**El protocolo mínimo antes de dar por bueno un script:**

1. **Prueba con datos reducidos** — no con el modelo de producción. Un archivo pequeño.
2. **Prueba con datos límite** — 0 elementos, 1 elemento, muchos elementos.
3. **Prueba con datos "malos"** — un dato faltante, un valor negativo, un texto donde iba número.
4. **Verifica manualmente** el output las primeras 2-3 veces. Después empiezas a confiar.
5. **Ten un "modo dry-run"** — un modo que solo lista lo que HARÍA sin hacerlo. Perfecto para revisiones antes de correr en producción.

**Ejemplo de dry-run:**

```python
def renombrar_familias(dry_run=False):
    for familia in obtener_familias():
        nuevo_nombre = calcular_nuevo(familia)
        if dry_run:
            print(f"[DRY] {familia.nombre} -> {nuevo_nombre}")
        else:
            familia.rename(nuevo_nombre)
```

Corres con `dry_run=True` primero, revisas la salida, y sólo si todo está bien lo corres de verdad.

</TopicCard>

<TopicCard step="8" title="8. Cómo escalar sin ahogarte (de script personal a herramienta del equipo)" time="~6 min">

Sigues este orden:

**Etapa 1 — Script personal** (semanas):
Un archivo. Sólo tú lo usas. Vale. No necesitas más.

**Etapa 2 — Herramienta compartida** (meses):
Ya lo usan 2-3 personas. Ahora sí: métele a Git, ponlo en carpetas, documenta las tres cosas críticas (cómo instalar, cómo usar, cuándo NO usarlo).

**Etapa 3 — Producto del equipo** (semestre):
Ya lo usan 10+ personas. Toca: instalador, versión, canal de soporte (aunque sea WhatsApp), reglas de contribución.

**Etapa 4 — Herramienta del rubro** (año o más):
Ya se distribuye a clientes externos. Necesitas: firma digital, updates automáticos, tests, licenciamiento. Y ahí es donde una mentoría o socio técnico ahorra semanas de errores.

## El resumen honesto — visión end to end

Programar como ingeniero civil es un camino de tres años que **empieza a dar retorno desde la primera semana**:

- **Mes 1:** primer script funciona. Ahorras 2 horas a la semana. Ganas confianza.
- **Mes 3:** ya usas Git, tienes 3-4 scripts útiles. El equipo empieza a pedirte cosas.
- **Mes 6:** dominas los patrones. Automatizas cosas serias. Tu jefe te ve distinto.
- **Año 1:** eres el "ingeniero-programador" del equipo. Tus decisiones pesan más. Tu compensación sube.
- **Año 2-3:** puedes independizarte, montar tu oficina automatizada, o liderar la transformación digital de la empresa. Tres carreras al alcance.

Y todo eso **sin dejar de ser ingeniero civil**. Al contrario: eres **mejor** ingeniero porque piensas con más claridad.
