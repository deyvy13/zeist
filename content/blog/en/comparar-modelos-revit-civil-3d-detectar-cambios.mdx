<Callout type="success" title="Quick answer">
To **compare two Revit or Civil 3D models**, you extract a fingerprint of every element from each version — unique ID, category, parameters and geometry — and match the two lists. The result classifies each element as **added, deleted, moved or modified**, showing which parameter changed with its old and new value. Revit has no complete in-app model comparison, and AutoCAD's DWG Compare inside Civil 3D compares geometry, not Civil 3D object data. That's why companies that exchange models daily use a **model comparison plugin** that produces the change report in minutes.
</Callout>

<Callout type="info" title="Glossary: the terms you'll read, in plain language">
- **Version or revision** — Each delivery of the model. Version A you had, version B you just received.
- **Unique ID** — The internal code Revit and Civil 3D assign to every element, which doesn't change when you move it. It's how you recognize "the same wall" in two versions.
- **Parameter** — Any piece of data on an element: material, section, level, diameter, elevation.
- **Delta** — The list of differences between two versions.
- **Linked model** — Another discipline's model loaded into yours as a reference.
- **BCF** — The open format for exchanging coordination issues between programs.
- **Plugin** — A program installed inside Revit or Civil 3D that adds its own buttons to the toolbar at the top.

No programming jargon. This is written for BIM coordinators, project managers and design managers.
</Callout>

## The cost nobody budgets for: finding the change

On a mid-size project, models are exchanged every week. Structure sends a version to architecture; MEP to structure; survey updates the surface; the contractor sends the model back with field adjustments.

It almost never arrives with a reliable change log. It arrives with an email: *"Here's the updated version."*

So someone — usually the most senior person on the team — opens both versions side by side and starts looking. View by view. Level by level. With the constant feeling that something is slipping through.

What slips through is the expensive part:

- **A beam that changed section** while the formwork drawing kept the old one.
- **A deleted wall** that still counts in the quantity takeoff.
- **A pipe that dropped 12 inches** and now clashes with a footing.
- **A scope change** nobody logged as a change order — and the company ended up absorbing it.

<TopicCard step="1" title="1. What 'comparing two models' really means" time="~5 min">

Comparing models isn't overlaying two views and hunting for differences. It's answering four questions for **every element**:

**Does it exist in both versions?** If only in the new one, it's **added**. If only in the old one, it's **deleted**.

**Is it in the same place?** If its location changed, it's **moved** — and you need to know by how much and in which direction.

**Does it carry the same data?** If a parameter changed — section, material, level, diameter, elevation — it's **modified**, and you need the parameter, its old value and its new value.

**Does the change matter?** An element that moved 0.004 inches from rounding isn't a real change. A tolerance filter separates noise from what affects the project.

<TopicCard step="2" title="2. What Revit and Civil 3D offer natively" time="~7 min">

There are tools, and they're worth knowing before building anything. Each solves part of the problem.

**In Revit:**

- **Copy/Monitor and Coordination Review.** Revit can monitor certain elements of a linked model — levels, grids, columns, walls, floors — and flag when they change. Useful, but only for elements set up for monitoring, and it doesn't produce a full model report.
- **Version comparison in Autodesk Docs.** If the project lives in Autodesk's cloud, the viewer can compare two published versions and mark added, deleted and modified items. Good for a visual review; it depends on working on that platform.
- **Navisworks.** Has a model comparison tool and is the coordination standard. It requires exporting and working outside Revit.

**In Civil 3D:**

- **DWG Compare.** Comes from AutoCAD and highlights graphical differences between two DWGs. It compares **geometry**, not Civil 3D object data: it won't tell you an alignment changed between stations 12+00 and 14+50, or that a pipe changed diameter.
- **Volume surface.** For surfaces there's an excellent native answer: a difference surface between the old and new version shows where and by how much the ground changed.

If you work in Autodesk's cloud and a visual review is enough, use it. When you need an **auditable report** — what changed, by how much, and in which parameter — to approve deliverables, control change orders or update takeoffs, that's where a plugin comes in.

<TopicCard step="3" title="3. How a comparison plugin works, step by step" time="~8 min">

This is what happens behind the button. It's worth understanding because it explains why the result is reliable.

**1. Fingerprint the old version.** It walks the model and stores, for each element: its unique ID, category and type, the parameters your company defined as relevant, and a geometry signature (location, dimensions, length or volume).

**2. Fingerprint the new version.** With the same rules, so the comparison is fair.

**3. Match elements.** First by unique ID, the most reliable key. When another team rebuilt part of the model and IDs changed, it matches by type and location and flags it as *matched by position* for someone to confirm.

**4. Classify each element.** Added, deleted, moved or modified. For modified ones, it records which parameter changed, the old value and the new one.

**5. Filter the noise.** It applies tolerances — for example, ignoring movements under 1 mm — and drops parameters that change on their own, like edit dates.

**6. Deliver the result.** A color-coded 3D view inside the program (green added, red deleted, amber modified), an Excel report filterable by discipline and level, and BCF issues to send to the responsible team.

<Callout type="success" title="The detail that makes the difference">
A good plugin doesn't just say *what* changed: it says **what's affected**. If a beam changed section, it lists the sheets where it appears and the takeoff item that moves. That turns a technical list into a management decision.
</Callout>

<TopicCard step="4" title="4. In Civil 3D: comparing alignments, surfaces and networks" time="~7 min">

In infrastructure, the important changes aren't "one object more or less": they're changes **inside** objects. So a Civil 3D comparison has to understand each type.

**Alignments.** Detects the segments where the geometry changed and reports them by station: *"between 12+00 and 14+50, curve C-7 radius changed from 500 ft to 400 ft"*.

**Profiles.** Grades, vertical curves and finished-grade elevations that changed, also by station.

**Surfaces.** The elevation difference between versions, with the cut and fill volume that moved. It tells you whether the ground change affects your earthwork.

**Pipe networks.** Pipes added or removed, changes in diameter, material, slope and invert; structures that moved.

**Corridors.** Regions and assemblies that changed — where the biggest quantity changes hide.

<Callout type="warn" title="Why it matters on public projects">
Every change between versions moves quantities. If nobody documents them, the takeoff in the latest submittal won't match the model, and that's exactly what triggers review comments. A per-version change report is also your **backup** when a change order has to be justified.
</Callout>

</TopicCard>

<TopicCard step="5" title="5. Where it pays for itself: the three uses that save the most" time="~6 min">

**1. Receiving third-party deliverables.** When a consultant or subcontractor delivers a version, the change report is the first review: in minutes you know whether what was agreed changed, whether something that shouldn't have changed did, and what needs re-checking. Review stops depending on someone's memory.

**2. Controlling change orders.** Scope changes show up as added or modified elements between versions. With the report, every change order has its evidence: what changed, when, and in which version. Without it, many changes get absorbed instead of billed.

**3. Updating drawings and takeoffs.** Knowing exactly what changed lets you review only what's affected, instead of re-checking the whole project on every version.

<TopicCard step="6" title="6. How to roll it out in your company" time="~5 min">

**Step 1 · Define what a change means to you.** Which categories and parameters matter per discipline, and which tolerances to apply. This page is what turns the plugin into your tool rather than a generic one.

**Step 2 · Keep IDs stable.** Ask teams to work on the same model instead of rebuilding it, and not to copy-paste elements between files. That preserves IDs and makes the comparison exact.

**Step 3 · Test it on two real versions.** Take two deliveries from a closed project where you already know what changed. If the report finds what you found — and more — it's ready.

**Step 4 · Make it part of intake.** Every version that comes in goes through the comparison before being accepted. The report is filed with the deliverable.

</TopicCard>
