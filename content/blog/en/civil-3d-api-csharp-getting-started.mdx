<Callout type="success" title="Quick answer">
The Civil 3D API is the official interface that lets a **C#** program read and modify alignments, profiles, surfaces, corridors, COGO points and pipe networks. It runs on .NET and on top of the AutoCAD API: a plugin references the AutoCAD libraries (AcCoreMgd, AcDbMgd and AcMgd) and the Civil 3D ones (AecBaseMgd and AeccDbMgd). The entry point is `CivilApplication.ActiveDocument`. You program it in the free Visual Studio Community: Civil 3D 2025 and 2026 use .NET 8, and 2027 uses .NET 10. The plugin loads with the NETLOAD command or as a bundle.
</Callout>

<Callout type="info" title="Glossary: the terms you'll read, in plain words">
- **API** — The list of things a program can ask Civil 3D to do. Like a restaurant menu: if it's on the menu, you can order it.
- **C# and .NET** — The Microsoft language and platform used to build Civil 3D plugins.
- **Library or DLL** — A file with ready-to-use code. Civil 3D ships its own; your plugin will be a DLL too.
- **Reference** — Telling your project which Autodesk libraries it will use.
- **Transaction** — The block in which you read or modify the drawing. It's committed or discarded as a whole.
- **ObjectId** — The number Civil 3D uses to identify each object in the drawing.
- **Command** — What you type at the command line to run your code.

Written for civil engineers and BIM coordinators who have never programmed Civil 3D.
</Callout>

## Why so few people program Civil 3D

There's plenty of material on the Revit API and little on Civil 3D's. It's not that Civil 3D has less to automate: a roadway plan set repeats as much work as a building. It's that the Civil 3D API has more layers, its objects are more complex, and its documentation has fewer examples.

This guide covers the minimum to start right: what it is, what to install, a real first command, and the errors worth knowing before you trip over them.

<TopicCard step="1" title="1. What the Civil 3D API is, and the alternatives" time="~5 min">

Civil 3D is built on AutoCAD, and so is its API. A Civil 3D program uses **two layers**:

- **The AutoCAD .NET API:** documents, transactions, the command line, lines, polylines, blocks and layers.
- **The Civil 3D .NET API:** the engineering objects: alignments, profiles, surfaces, corridors, sections, COGO points, parcels and pipe networks.

**The alternatives, depending on what you need:**

- **Dynamo**, to automate without writing code. Since Civil 3D 2025.1 it ships more than a thousand out-of-the-box nodes; we cover it in [10 Dynamo scripts for Civil 3D](/en/blog/dynamo-civil-3d-scripts).
- **Python**, inside Dynamo's Python nodes, when the visual nodes fall short.
- **The COM API**, older, still used by some LISP and VBA routines.
- **C# on the .NET API**, for production tools the whole office uses. That's the path in this guide.

</TopicCard>

<TopicCard step="2" title="2. What you need before writing code" time="~6 min">

1. **Windows with Civil 3D installed.** The API only runs inside Civil 3D.
2. **Visual Studio Community**, free, with the .NET desktop development workload.
3. **The right framework for your release:**

| Civil 3D release | Framework |
|---|---|
| 2024 and earlier | .NET Framework 4.8 |
| 2025 and 2026 | .NET 8 |
| 2027 | .NET 10 |

4. **A class library project**, referencing the libraries in the Civil 3D install folder: AcCoreMgd, AcDbMgd and AcMgd from AutoCAD, and AecBaseMgd and AeccDbMgd from Civil 3D.

<Callout type="warn" title="Copy Local: No">
On every Autodesk reference, **Copy Local** must be set to **No**. If they're copied into your plugin's folder, Civil 3D may load two versions of the same library and fail in ways that are hard to diagnose.
</Callout>

</TopicCard>

<TopicCard step="3" title="3. Your first command: list the alignments in the drawing" time="~8 min">

This command walks through the drawing's alignments and writes each name and length to the command line:

```csharp
using Autodesk.AutoCAD.ApplicationServices;
using Autodesk.AutoCAD.DatabaseServices;
using Autodesk.AutoCAD.EditorInput;
using Autodesk.AutoCAD.Runtime;
using Autodesk.Civil.ApplicationServices;
using Autodesk.Civil.DatabaseServices;

[assembly: CommandClass(typeof(ZeistDemo.Commands))]

namespace ZeistDemo
{
    public class Commands
    {
        [CommandMethod("ZLISTALIGNMENTS")]
        public void ListAlignments()
        {
            Document doc = Application.DocumentManager.MdiActiveDocument;
            Editor ed = doc.Editor;
            CivilDocument civil = CivilApplication.ActiveDocument;

            using (Transaction tr = doc.Database.TransactionManager.StartTransaction())
            {
                foreach (ObjectId id in civil.GetAlignmentIds())
                {
                    var alignment = (Alignment)tr.GetObject(id, OpenMode.ForRead);
                    ed.WriteMessage($"\n{alignment.Name}: {alignment.Length:F2}");
                }
                tr.Commit();
            }
        }
    }
}
```

**What each part does:**

- `CommandMethod` turns the method into a command you type in Civil 3D.
- `CivilApplication.ActiveDocument` gives access to the Civil 3D objects in the open drawing.
- `GetAlignmentIds()` returns the IDs of every alignment.
- The transaction opens each alignment for reading, and `Commit` closes it.

**To test it:** build, open Civil 3D with a drawing that has alignments, type `NETLOAD`, pick your DLL and run `ZLISTALIGNMENTS`.

</TopicCard>

<TopicCard step="4" title="4. The objects you'll use every time" time="~5 min">

Almost everything starts at the `CivilDocument`, the Civil 3D document of the open drawing:

| You want to work with | Starting point on CivilDocument |
|---|---|
| Alignments | GetAlignmentIds() |
| Surfaces | GetSurfaceIds() |
| Corridors | CorridorCollection |
| COGO points | CogoPoints |
| Pipe networks | GetPipeNetworkIds() |
| Styles | Styles |

From each alignment you reach its profiles and sample line groups; from each corridor, its baselines and regions. The pattern never changes: get the ID, open the object inside a transaction, then read or modify it. An example that creates sample lines from a station list is in [automated Civil 3D sample lines](/en/blog/civil-3d-sample-lines).

<Callout type="info" title="Where the official documentation is">
The Civil 3D Developer's Guide and API Reference are in Autodesk's help, and the Civil 3D Customization forum in the Autodesk Community is the best place for specific questions.
</Callout>

</TopicCard>

<TopicCard step="5" title="5. The errors of week one" time="~6 min">

- **"Cannot load assembly" on NETLOAD.** The project targets a different framework than your Civil 3D release uses. Check the table in step 2.
- **Odd errors when Civil 3D loads or closes.** The Autodesk references were left with Copy Local set to Yes.
- **Changes aren't saved.** `tr.Commit()` is missing: an uncommitted transaction is discarded entirely.
- **eLockViolation.** It happens when code runs from your own window instead of a command: lock the document before modifying it.
- **Works on your release, not on your colleague's.** Every Civil 3D release requires building against its own libraries.

</TopicCard>

<TopicCard step="6" title="6. From a command to a plugin the whole office uses" time="~5 min">

A command that works on your machine isn't a tool yet. For the office to use it you need:

- **A button on the Civil 3D top toolbar**, instead of a typed command.
- **A bundle**: the folder in Autodesk's official format that Civil 3D loads at startup.
- **Error handling and logging**, so a failure never leaves the drawing half-done.
- **A layered structure**, so an Autodesk release change touches only one part of the code.

We explain it in [Revit and Civil 3D add-in development](/en/blog/revit-civil-3d-add-in-development), and if you want to get there faster with AI, in [building a Civil 3D plugin with Claude Code](/en/blog/claude-code-civil-3d-plugin).
