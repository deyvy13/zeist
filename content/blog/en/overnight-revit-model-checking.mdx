<Callout type="success" title="Quick answer">
Yes, it can be done. A scheduled process opens each Revit model overnight, with nobody at the computer, measures warnings, file size, imported CAD and empty parameters, and leaves a report for the morning. You build it with Revit Batch Processor and Windows Task Scheduler, with Model Checker, with Design Automation in the cloud, or with a custom plugin.
</Callout>

<Callout type="info" title="Glossary: the terms you'll read, in plain English">
- **Model audit** — Checking a model against a list of rules: how heavy it is, how many errors it has, whether it meets the standard.
- **Warnings** — The alerts Revit accumulates in every model: overlapping walls, duplicate elements, unenclosed rooms.
- **Batch process** — A program that does the same task on many files, one after another.
- **Task Scheduler** — The Windows tool that runs a program at a set time.
- **Rule set** — The list of checks applied to each model. Model Checker calls it a checkset.
</Callout>

## How is this different from an audit checklist?

The [BIM audit checklist](/en/blog/bim-audit-checklist) reviews how the firm works **once**: processes, standards, hours. The guide to [slow Revit models](/en/blog/slow-revit-model) explains **why** a model degrades.

An automated audit does something else: it **measures the same things every night** on every model and keeps the history. You see when a problem started, and in which model, before the team feels it.

## What can you check without anyone opening Revit?

Anything you can count from the model:

| Indicator | What it measures | Why it matters |
|---|---|---|
| Warnings | How many, and of what type | Lots of warnings make a model unstable |
| File size | How much it grows each week | A sudden jump points to a recent problem |
| Imported CAD | Files imported instead of linked | The most common cause of heavy models |
| In-place families | How many there are | They're heavier and slow the model down |
| Views not on sheets | Views that aren't placed anywhere | They take up space and confuse people |
| Required parameters | Elements with empty data | The deliverable goes out incomplete |
| Naming | Views, sheets and families off-standard | The model gets hard to work with |

Warnings are the same list Revit shows in its Review Warnings dialog. A program reads all of it, with the type and the elements behind each one.

## Which tools can run it overnight?

| Route | How it runs | Pros | Cons |
|---|---|---|---|
| Revit Batch Processor | Desktop Revit from the command line, launched by Task Scheduler | Free and open source (GPL-3.0); runs Python or Dynamo scripts; Revit 2015 to 2027 | Only handles Revit dialogs in English; the original author can no longer support it |
| Model Checker | Rule sets built in its Configurator; report to Excel | Free for licensed Revit users; Autodesk documents an automated run driven by an XML file | Only checks what its rules allow; its API is no longer supported from version 10.0 (Revit 2026) |
| Design Automation for Revit | Headless Revit in Autodesk's cloud, running a C# plugin | No office computer tied up; opens Revit cloud models from Revit 2022 | Requires development and an Autodesk Platform Services account |
| Custom plugin | Your rules, your report, your alerts | Measures exactly your standard and keeps the history | It has to be built |

They combine well: a custom plugin run overnight through Revit Batch Processor is a common setup.

## What does the team get in the morning?

A report you read without opening Revit:

- **One row per model** with each indicator and its change since the night before.
- **Alerts** when something crosses the threshold you set: say, 20 % more warnings in a week, or a newly imported CAD file.
- **The element list** with IDs, so you go straight to the problem.
- **The history**, in Excel or a dashboard, to see each project's trend.

## What does it take to make it work?

1. **A computer with Revit and a license**, available overnight.
2. **Access to the models**, on the office network or in the cloud.
3. **Rules with clear thresholds**: what gets measured, and at what value it raises an alert.
4. **Protecting central models**: on workshared models the process works on a detached copy or a new local, never on the central.
5. **Testing on copies** before you let it run on its own.
