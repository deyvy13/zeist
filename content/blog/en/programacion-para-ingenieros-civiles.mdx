## The uncomfortable truth: learning to code will change your career

A civil engineer who knows how to code — even at a basic level — does the same tasks **in half the time.** And more importantly, can automate what takes coworkers hours. That asymmetry is huge.

- If you're an employee: **your value per hour goes up.** Engineers who automate get paid more.
- If you run your own office: **you increase capacity without hiring.**
- If you're a freelancer: **you deliver faster** and compete better on price or margin.

And the good news: **it has never been easier to learn, thanks to AI.** You don't need a master's degree.

<TopicCard step="1" title="1. Why coding changes your career as an engineer" time="~4 min">

The hard numbers:

- Repetitive tasks in a typical engineering office: **40-60% of the team's time.**
- Salary premium for engineers with coding skills: **+30-70%** depending on the region.
- Reduction in human error from automation: **60-90%** for typical tasks.

And above all: **it changes how you think.** You start seeing problems as systems — with inputs, processes, and outputs. That mindset, beyond the code itself, makes you a better engineer.

**What programming as a civil engineer does NOT mean:**
- It doesn't mean becoming a software developer.
- It doesn't mean leaving engineering.
- It doesn't mean learning 20 languages.
- It means **using programming as just another tool**, like AutoCAD or Excel — just as natural.

<TopicCard step="3" title="3. Simple architecture (nothing scary)" time="~7 min">

"Software architecture" sounds like something huge. For you, an engineer who automates things, it's WAY simpler. It boils down to this:

**One rule:** organize your code into **layers**, each doing exactly one thing.

<AnimatedFlow
  title="The 3 minimum layers"
  nodes="Input (UI)|Business logic|Interaction with the software (Revit/Civil 3D)"
  subs="Forms, buttons|Your own rules|Autodesk API"
/>

**Translating to folders in your project:**

```
MyPlugin/
  UI/              (forms, windows, buttons)
  Logic/           (your rules: "beams <3m don't count")
  Revit/           (everything that touches the API — SetParameter, GetElement)
  Program.cs       (entry point, wires up the 3 layers)
```

**Why does this matter?** Because the day Autodesk changes the API (and it always does), you only touch the `Revit/` folder. Your logic and UI stay intact. And if tomorrow you want to switch from C# to another language, your logic is reusable.

**Civil engineering analogy:** it's like designing a building with structure, architecture, and systems **kept separate**. If you need to change the plumbing, you don't redesign the structure. Same with code.

</TopicCard>

<TopicCard step="4" title="4. Clean code — explained with examples, not theory" time="~8 min">

"Clean code" comes down to 4 concrete habits:

**a) Names that tell the truth.**

Bad:

```python
def calc(x, y):
    return x * y * 0.18
```

Good:

```python
def calculate_tax(price, quantity):
    return price * quantity * TAX_RATE
```

The second one reads itself. The first forces you to guess what it does.

**b) Short functions that do ONE thing.**

Bad — one function that does 5 things: read a file, filter data, calculate, generate a report, send an email.

Good — 5 functions:

```python
def read_data(file): ...
def filter_by_category(data, cat): ...
def calculate_totals(data): ...
def generate_report(totals): ...
def send_email(report, recipient): ...
```

**c) Named constants, not magic numbers.**

Bad: `if age > 18:` (why 18? what does it mean?).

Good:

```python
LEGAL_AGE = 18
if age > LEGAL_AGE:
    ...
```

**d) Comments where they matter, not on the obvious.**

Bad:

```python
# Add 1
x = x + 1
```

Good:

```python
# Beams <3m don't count per internal standard DGA-2023
if beam_length >= MINIMUM_BEAM_LENGTH:
    counter += 1
```

</TopicCard>

<TopicCard step="5" title="5. Reusable components — write once, use five times" time="~6 min">

**The problem:** every script starts from scratch. You copy-paste the same 30 lines every time to connect to Excel, read a file, or build a report.

**The solution:** the second time you write the same thing, it's a function. The third time, it's a component.

**Real example:** all your scripts end up exporting to Excel with the same corporate letterhead. Extract that code into a function you can import:

```python
# file: helpers/corporate_excel.py
def export_with_letterhead(data, path):
    """Exports a list of data to an Excel file with the
    company's corporate letterhead and styles."""
    ...
```

Now, in any script: `from helpers.corporate_excel import export_with_letterhead`. One line, not 30.

**Compound effect:** with 6-8 well-built components, every new script takes **1/3 of the time.** And they all automatically share the same corporate standard.

**Golden rule:** every time you copy and paste code, stop and ask yourself: "does this deserve to be a function?" Most of the time, yes.

</TopicCard>

<TopicCard step="6" title="6. Version control without the drama (Git in 20 minutes)" time="~4 min">

If you only learn one tool from this guide, make it Git. It's the **infinite backup** for your code.

**Easy setup (no terminal needed):**

1. Install **GitHub Desktop** (visual interface, free).
2. Create a free account at GitHub.com.
3. Create a private repository for each automation project.
4. Every time something works: **"Commit" button → "Push" button.** Done. It's saved in the cloud.

**What you gain:**

- If you break something tomorrow, you roll back to yesterday's version with one click.
- You can work from another machine and everything is synced.
- If you're sharing with a colleague, it's just a URL.
- **Never again "I lost the file."**

Total cost of learning it well: 20 minutes plus a YouTube video. Value: infinite.

</TopicCard>

<TopicCard step="7" title="7. Minimal manual testing (you don't need to become QA)" time="~5 min">

You don't need to write automated tests like a senior dev. You need **a minimum amount of discipline** so you don't break things.

**The minimum protocol before signing off on a script:**

1. **Test with a small dataset** — not the production model. A small file.
2. **Test with edge cases** — 0 elements, 1 element, many elements.
3. **Test with "bad" data** — a missing value, a negative number, text where a number was expected.
4. **Manually verify** the output the first 2-3 times. After that, you can start trusting it.
5. **Have a "dry-run mode"** — a mode that only lists what it WOULD do, without doing it. Perfect for reviewing before running it on production.

**Dry-run example:**

```python
def rename_families(dry_run=False):
    for family in get_families():
        new_name = calculate_new_name(family)
        if dry_run:
            print(f"[DRY] {family.name} -> {new_name}")
        else:
            family.rename(new_name)
```

Run it with `dry_run=True` first, check the output, and only run it for real once everything looks right.

</TopicCard>

<TopicCard step="8" title="8. How to scale without drowning (from personal script to team tool)" time="~6 min">

Follow this order:

**Stage 1 — Personal script** (weeks):
A single file. Only you use it. That's fine. You don't need more.

**Stage 2 — Shared tool** (months):
2-3 people already use it. Now it's time to: put it in Git, organize it into folders, document the three critical things (how to install it, how to use it, when NOT to use it).

**Stage 3 — Team product** (half a year):
10+ people already use it. Time for: an installer, versioning, a support channel (even if it's just WhatsApp), contribution rules.

**Stage 4 — Industry tool** (a year or more):
It's already being distributed to external clients. You need: a digital signature, automatic updates, tests, licensing. This is where a mentorship or technical partner saves you weeks of mistakes.

<AnimatedFlow
  title="The four stages"
  nodes="Personal|Shared|Product|Industry"
  subs="Just you|2-5 people|10+ users|External users"
/>

**Key rule:** don't skip stages ahead of time. A script only you use **doesn't need an installer.** A product used by 20 people **can't survive without Git.** Match the discipline to the moment.

</TopicCard>
