## A verdade incômoda: programar vai mudar sua carreira

Um engenheiro civil que sabe programar (mesmo básico) faz as mesmas tarefas **na metade do tempo**. E o mais importante: pode automatizar o que aos colegas leva horas. Essa assimetria é enorme.

- Se é empregado: **aumenta seu valor por hora**. Engenheiros que automatizam ganham mais.
- Se tem escritório próprio: **aumenta capacidade sem contratar**.
- Se é freelancer: **entrega mais rápido** e compete melhor em preço ou margem.

E a parte boa: **com IA nunca foi tão fácil aprender**. Não precisa de mestrado.

<TopicCard step="1" title="1. Por que programar muda sua carreira de engenheiro civil" time="~4 min">

Dados duros:

- Tarefas repetitivas num escritório de engenharia típico: **40-60% do tempo da equipe**.
- Salário premium de engenheiros com habilidades de programação: **+30-70%** conforme a região.
- Redução de erros humanos automatizando: **60-90%** para tarefas típicas.

E acima de tudo: **te muda o chip**. Você começa a ver problemas como sistemas — com inputs, processos e outputs. Essa mentalidade, além do código, te faz melhor engenheiro.

**O que NÃO significa programar como engenheiro civil:**
- Não significa virar desenvolvedor de software.
- Não significa largar a engenharia.
- Não significa aprender 20 linguagens.
- Significa **usar programação como mais uma ferramenta**, como AutoCAD ou Excel — igual de natural.

<TopicCard step="3" title="3. Arquitetura simples (sem susto)" time="~7 min">

"Arquitetura de software" soa como algo enorme. Para você, engenheiro que automatiza, é MUITÍSSIMO mais simples. Se resume em:

**Regra única:** organize seu código em **camadas** que fazem uma coisa só cada uma.

<AnimatedFlow
  title="As 3 camadas mínimas"
  nodes="Entrada (UI)|Lógica do negócio|Interação com o software (Revit/Civil 3D)"
  subs="Formulários, botões|Regras próprias|API da Autodesk"
/>

**Tradução para pastas do seu projeto:**

```
MeuPlugin/
  UI/              (formulários, janelas, botões)
  Logic/           (suas regras: "vigas <3m não contam")
  Revit/           (tudo que toca a API — SetParameter, GetElement)
  Program.cs       (ponto de entrada, monta as 3 camadas)
```

**Por que isso importa?** Porque no dia que a Autodesk mudar a API (e sempre muda), você só toca a pasta `Revit/`. Sua lógica e UI ficam intactas. E se amanhã quiser trocar de C# para outra linguagem, sua lógica é reaproveitável.

**Analogia civil:** é como projetar um edifício com estrutura, arquitetura e instalações **separadas**. Se toca mudar as instalações, não redesenha a estrutura. Com código igual.

</TopicCard>

<TopicCard step="4" title="4. Código limpo — explicado com exemplos, não teoria" time="~8 min">

"Código limpo" são 4 hábitos concretos:

**a) Nomes que dizem a verdade.**

Ruim:

```python
def calc(x, y):
    return x * y * 0.18
```

Bom:

```python
def calcular_imposto(preco, quantidade):
    return preco * quantidade * TAXA_IMPOSTO
```

O segundo se lê. O primeiro te obriga a adivinhar o que faz.

**b) Funções curtas que fazem UMA coisa.**

Ruim — uma função que faz 5 coisas: ler arquivo, filtrar dados, calcular, gerar relatório, enviar email.

Bom — 5 funções:

```python
def ler_dados(arquivo): ...
def filtrar_por_categoria(dados, cat): ...
def calcular_totais(dados): ...
def gerar_relatorio(totais): ...
def enviar_email(relatorio, destinatario): ...
```

**c) Constantes com nome, não números mágicos.**

Ruim: `if idade > 18:` (por que 18? o que significa?).

Bom:

```python
IDADE_MAIORIDADE = 18
if idade > IDADE_MAIORIDADE:
    ...
```

**d) Comentários onde importam, não no óbvio.**

Ruim:

```python
# Somar 1
x = x + 1
```

Bom:

```python
# Vigas <3m não contam por norma interna DGA-2023
if comprimento_viga >= COMPRIMENTO_MINIMO_VIGA:
    contador += 1
```

</TopicCard>

<TopicCard step="5" title="5. Componentes reutilizáveis — escreva uma vez, use cinco vezes" time="~6 min">

**O problema:** cada script começa do zero. Você copia e cola as mesmas 30 linhas de sempre para conectar com Excel, para ler um arquivo, para montar um relatório.

**A solução:** quando escrever a mesma coisa **duas vezes**, é uma função. Na terceira, é um componente.

**Exemplo real:** todos seus scripts terminam exportando para Excel com o mesmo selo corporativo. Extraia esse código para uma função que possa importar:

```python
# arquivo: helpers/excel_corporativo.py
def exportar_com_selo(dados, caminho):
    """Exporta uma lista de dados para um Excel com o
    selo e estilos corporativos da empresa."""
    ...
```

Agora em qualquer script: `from helpers.excel_corporativo import exportar_com_selo`. Uma linha, não 30.

**Efeito composto:** com 6-8 componentes bem feitos, cada novo script leva **1/3 do tempo**. E todos compartilham o mesmo padrão corporativo automaticamente.

**Regra de ouro:** sempre que copiar e colar código, pare e pergunte: "isso merece ser uma função?". A maioria das vezes, sim.

</TopicCard>

<TopicCard step="6" title="6. Controle de versão sem drama (Git em 20 minutos)" time="~4 min">

Se só aprender uma ferramenta deste guia, que seja Git. É o **backup infinito** do seu código.

**Setup fácil (sem terminal):**

1. Instale **GitHub Desktop** (interface visual, gratuito).
2. Crie uma conta em GitHub.com (grátis).
3. Crie um repositório privado para cada projeto de automação.
4. Sempre que algo funciona: **botão "Commit" → botão "Push"**. Pronto. Está salvo na nuvem.

**O que você ganha:**

- Se amanhã quebrar algo, volta para a versão de ontem com um botão.
- Trabalha de outra máquina e tudo está sincronizado.
- Se vai compartilhar com um colega, é uma URL.
- **Nunca mais "perdi o arquivo"**.

Custo total de aprender bem: 20 minutos + um vídeo do YouTube. Valor: infinito.

</TopicCard>

<TopicCard step="7" title="7. Testes manuais mínimos (não vire QA)" time="~5 min">

Você não precisa escrever testes automatizados como um dev sênior. Precisa de **um mínimo de disciplina** para não quebrar coisas.

**O protocolo mínimo antes de dar como bom um script:**

1. **Teste com dados reduzidos** — não com o modelo de produção. Um arquivo pequeno.
2. **Teste com dados limite** — 0 elementos, 1 elemento, muitos elementos.
3. **Teste com dados "ruins"** — um dado faltando, um valor negativo, um texto onde ia número.
4. **Verifique manualmente** o output nas primeiras 2-3 vezes. Depois começa a confiar.
5. **Tenha um "modo dry-run"** — um modo que só lista o que FARIA sem fazer. Perfeito para revisões antes de rodar em produção.

**Exemplo de dry-run:**

```python
def renomear_familias(dry_run=False):
    for familia in obter_familias():
        novo_nome = calcular_novo(familia)
        if dry_run:
            print(f"[DRY] {familia.nome} -> {novo_nome}")
        else:
            familia.rename(novo_nome)
```

Roda com `dry_run=True` primeiro, revisa a saída, e só se estiver tudo bem roda de verdade.

</TopicCard>

<TopicCard step="8" title="8. Como escalar sem se afogar (de script pessoal a ferramenta da equipe)" time="~6 min">

Siga esta ordem:

**Etapa 1 — Script pessoal** (semanas):
Um arquivo. Só você usa. Vale. Não precisa mais.

**Etapa 2 — Ferramenta compartilhada** (meses):
Já usam 2-3 pessoas. Agora sim: coloca no Git, organiza em pastas, documenta as três coisas críticas (como instalar, como usar, quando NÃO usar).

**Etapa 3 — Produto da equipe** (semestre):
Já usam 10+ pessoas. Toca: instalador, versão, canal de suporte (mesmo que WhatsApp), regras de contribuição.

**Etapa 4 — Ferramenta do setor** (ano ou mais):
Já é distribuída a clientes externos. Precisa: assinatura digital, updates automáticos, testes, licenciamento. E é aí que uma mentoria ou parceiro técnico economiza semanas de erros.

**Regra chave:** não pule de etapa antes da hora. Um script que só você usa **não precisa de instalador**. Um produto que 20 pessoas usam **não sobrevive sem Git**. Ajuste a disciplina ao momento.

## O resumo honesto — visão end to end

Programar como engenheiro civil é um caminho de três anos que **começa a dar retorno desde a primeira semana**:

- **Mês 1:** primeiro script funciona. Economiza 2 horas por semana. Ganha confiança.
- **Mês 3:** já usa Git, tem 3-4 scripts úteis. A equipe começa a te pedir coisas.
- **Mês 6:** domina os padrões. Automatiza coisas sérias. Seu chefe te vê diferente.
- **Ano 1:** é o "engenheiro-programador" da equipe. Suas decisões pesam mais. Sua remuneração sobe.
- **Ano 2-3:** pode se independizar, montar seu escritório automatizado, ou liderar a transformação digital da empresa. Três carreiras ao alcance.

E tudo isso **sem deixar de ser engenheiro civil**. Ao contrário: é **melhor** engenheiro porque pensa com mais clareza.
